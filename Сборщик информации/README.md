# Сборщик информации

Небольшое локальное приложение на Python для подготовки ежедневной сводки из заранее выбранных источников. Оно собирает доступные RSS/API-материалы и записи, внесённые вручную, нормализует ссылки и даты, удаляет дубли, формирует черновик с атрибуцией каждого источника и ждёт редакторского одобрения перед публикацией в MAX.

## Структура

```text
Сборщик информации/
  app/                  исходный код приложения
  data/                 база SQLite и очередь черновиков (создаются при запуске)
  README.md             установка и руководство
  EDITORIAL_POLICY.md   правила отбора, проверки и исправления сообщений
  requirements.txt      зависимости
  .env.example          пример переменных MAX API
```

Приложение по умолчанию использует уже созданный `../sources.yaml`. Путь можно переопределить переменной `SOURCES_FILE`. `enabled: false` отключает автоматическое получение, но не мешает добавить материал вручную через `ingest`. Автоматически включён только ранее проверенный GOV.UK Atom feed. Для OCHA подготовлен адаптер публичного ReliefWeb API, но источник оставлен выключенным до получения предварительно одобренного ReliefWeb `appname` и его настройки в `RELIEFWEB_APPNAME`. Ленты BBC, Reuters и аналитических проектов не включаются только по факту наличия URL: сначала нужны разрешённый способ доступа и проверка условий использования. API ReliefWeb может возвращать материалы партнёров с собственными авторскими правами; сборщик получает только заголовок, дату, URL и метаданные, а в канал публикуются краткие атрибутированные формулировки со ссылкой.

### Оценка релевантности и контроль полноты

Для каждого RSS/API-источника правила в `sources.yaml` задают отдельные словари географии, военной тематики и сильных фраз. Сопоставление не зависит от регистра и ищет целые слова/фразы, чтобы избежать случайных подстрочных совпадений. Сильный тематический признак либо сочетание географии и военного контекста получает высокую уверенность и становится кандидатом для черновика. Частичное совпадение и отсутствие совпадений не приводят к молчаливому удалению: материал сохраняется в очереди релевантности, но не попадает в черновик до решения редактора.

```powershell
python -m app review relevance --status review
python -m app review relevance-check ID --include --note "В тексте описано событие на линии фронта"
python -m app review relevance-check ID --exclude --note "Материал не относится к сводке о линии фронта"
python -m app review filter-report --days 7
```

`review relevance` показывает материал, уверенность, причину и совпавшие термины. Редакторские включения и исключения остаются в журнале. `filter-report` агрегирует число записей из лент, кандидатов с высокой уверенностью, ожидающих проверки материалов, дублей и ошибок; также показывает низкоуверенные материалы, которые редактор всё же включил, как возможные пропуски фильтра. Эти цифры оценивают работу фильтра, но не доказывают, что найден каждый релевантный материал.

## Установка

Требуется Python 3.11 или новее.

Для семантической группировки приложение локально использует мультиязычную модель Sentence Transformers. При первой сборке с несколькими материалами модель будет загружена из Hugging Face и сохранена в локальный кэш; последующие сравнения выполняются на компьютере. Для этой загрузки нужно интернет-соединение. Можно задать модель через `EVENT_MATCH_MODEL`, а порог сходства — через `EVENT_MATCH_THRESHOLD` (по умолчанию `0.70`). Заголовки и описания при сравнении не отправляются внешнему AI-сервису.

```powershell
cd "C:\projects\project_1\Сборщик информации"
py -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## Текущий рабочий процесс

1. Для автоматического получения явно включить разрешённый RSS/API в `sources.yaml`. `manual`-источники можно добавлять через `ingest`, даже если автоматический сбор для них выключен.
2. Запустить сбор доступных RSS/API-источников: `python -m app fetch`.
3. Добавить проверенные вручную материалы:

```powershell
python -m app ingest --source ru_mod --title "Заголовок сообщения" --url "https://example.org/story" --published-at "2026-10-11T09:30:00+03:00" --summary "Краткое описание своими словами"
```

4. Создать черновик из материалов, опубликованных за последние 24 часа: `python -m app draft`. Расширить период можно явно: `--hours 96`; материалы старше суток попадут в отдельный блок. Если вся сводка не помещается в лимит MAX, приложение готовит несколько частей, каждая не длиннее 4000 символов, и выводит ID всех частей. Утверждение и его ссылка остаются вместе. Просмотрите все части через `python -m app review list`; дневной лимит по-прежнему разрешает опубликовать только один основной пост, поэтому одобряйте не более одной части за день. Плановая публикация пропустит отправку, если на этот день одобрено несколько основных черновиков. Для каждого пункта приложение хранит дату публикации отдельно от даты события и не пытается автоматически выводить одну из другой.
5. Просмотреть очередь: `python -m app review list`, затем `python -m app review show ID`. Просмотр показывает текст поста и отдельный список утверждений с ID, источником, датой публикации, датой события и ссылкой, а также номер группы-кандидата.
   Материалы сохраняются версиями. Повторный сбор без изменений обновляет только время последней проверки; изменение заголовка, описания или даты публикации создаёт новую версию и не перезаписывает прежнюю. В `review show` отображаются версия утверждения и предупреждения о более свежей редакции источника. Если новая версия относится к уже опубликованному посту, ссылка на этот пост записывается в событие `source_revision_detected` в журнале; приложение не меняет пост и не решает автоматически, нужно ли исправление. Если редактор считает его необходимым, черновик исправления можно подготовить командой `correct`.
   Для каждого предупреждения откройте источник и выберите решение: `python -m app review revision-check DRAFT_ID CLAIM_ID --keep-current --note "Новая версия проверена; прежнее утверждение остаётся верным"` сохраняет прежнюю формулировку и считает новую версию уже рассмотренной; `--refresh --note "Формулировка и дата сверены с новой версией"` подставляет новый заголовок и дату публикации, сбрасывает проверки ссылки, даты события и группы, после чего их нужно выполнить заново. Если прежнее утверждение больше не подходит, исключите его; новая версия станет доступна для следующего черновика. Неодобренный черновик нельзя одобрить, пока предупреждение не разрешено.
6. Для каждого утверждения выясните дату самого события, читая материал. Укажите точную дату командой `python -m app review event-date DRAFT_ID CLAIM_ID --date YYYY-MM-DD --note "Дата указана в тексте источника"`. Если редактор проверил, что событие произошло в день публикации, используйте `--same-day`; дата публикации сама по себе такого вывода не даёт. Если дату установить не удалось, укажите `--unknown`, затем исключите утверждение командой `python -m app review claim-exclude DRAFT_ID CLAIM_ID --reason "Дату события установить не удалось"`. Неизвестная дата блокирует одобрение, пока пункт остаётся в посте.
7. Откройте ссылку каждого оставшегося утверждения, проверьте, что материал действительно содержит именно его, и зафиксируйте проверку отдельно для каждого ID: `python -m app review claim-check DRAFT_ID CLAIM_ID --checked`. Одной ссылки в соседней строке для других утверждений недостаточно.
8. Для каждой группы из двух или более оставшихся утверждений используйте номер группы из `review show` и отдельно зафиксируйте оба решения. Пример: `python -m app review group-check ID 1 --same-event --independent --note "Сопоставлены тексты и первичные ссылки"`. Если это разные события, укажите `--different-events`; если независимость не подтверждена — `--not-independent`. В любом случае краткое обоснование обязательно. Утверждения и ссылки остаются раздельными пунктами поста; отрицательное решение не превращает их в общий факт.
9. При необходимости исправить текст: `python -m app review edit ID --text "..."`. Одобрение заблокируется, если из текста удалено сохранённое утверждение, его собственная ссылка или указанная рядом дата события.
10. Проверьте содержание и остальные редакционные условия. Одобрить можно только после проверки даты события, каждой ссылки и групп-кандидатов: `python -m app review approve ID --evidence-checked --independence-checked`.
11. Только после одобрения опубликовать: `python -m app publish ID`.

Для исправления опубликованного поста подготовьте связанный заметный черновик: `python -m app correct ID --reason "что было неверно" --corrected "исправленная информация" --source-url "https://example.org/evidence"`. Проверьте, одобрите и опубликуйте его обычным способом. Исправления связаны с исходным постом и не занимают дневной слот основного поста. Если результат отправки в MAX неизвестен из-за обрыва сети, сначала проверьте канал и выполните `python -m app publish-resolve ID --posted --url "ССЫЛКА"` либо `python -m app publish-resolve ID --not-posted`; второй вариант освобождает слот, если проверка подтвердила, что поста нет.

Каждое утверждение в черновике выводится отдельно со своей ссылкой и датой события. Объединение означает только «возможно, одно событие» и само по себе не подтверждает факт или независимость публикаций. Приложение не генерирует автоматически военные оценки или прогнозы: оно формирует атрибутированные формулировки из заголовков.

Перед редактурой и одобрением черновика применяйте [редакционные правила](EDITORIAL_POLICY.md). Материалы с похожими заголовками в выбранном временном окне приложение может сгруппировать. Внутри группы сохраняются отдельные атрибутированные заявления и отдельные ссылки, поэтому заголовок одной публикации не подаётся как утверждение всех остальных источников. Группировка остаётся эвристикой: редактор обязан проверить, что это одно событие, и при необходимости исправить объединение.

Уровни источников сами по себе не дают автоматический статус «подтверждено». До редакторской проверки каждое утверждение остаётся атрибутированным конкретному источнику; приложение не устанавливает, не перепечатал ли другой источник то же заявление. Аналитические материалы должны быть обозначены как оценка автора.

Семантическая модель группирует только кандидатов в одно событие; сходство текста не доказывает тождество событий. Перед одобрением редактор фиксирует решение по каждой группе через `review group-check`, а также отдельно проверяет ссылку каждого утверждения через `review claim-check`. Эти отметки сохраняются в структурированных таблицах и журнале; они фиксируют выполненную проверку, но сами по себе не доказывают истинность утверждений.

Для проверки публикации сборщик сверяет домен ссылки с `allowed_domains` в `sources.yaml` и дату, затем делает HTTP HEAD-запрос без загрузки текста страницы. Для RSS/Atom/API сохраняется способ получения записи. При HTTP 404/410 материал отклоняется; при 403/405, сетевой ошибке или тайм-ауте черновик помечает ссылку для ручной проверки. Это подтверждает домен и доступность страницы, но не совпадение её текста с заголовком и не истинность описанных фактов.

Одобрение обычного черновика проверяет отдельную запись для каждого утверждения: текст, источник, дату публикации, действительную HTTP(S)-ссылку, редакторскую отметку о соответствии ссылки утверждению и проверенную дату события. Даты публикации и события хранятся отдельно. Если дату события установить нельзя, пункт нужно исключить; такое решение и причина остаются в базе и журнале. Текст, ссылка и дата события каждого оставшегося утверждения должны присутствовать рядом в теле поста. Для каждой группы-кандидата приложение требует отдельные сохранённые решения редактора «одно событие / разные события» и «независимые источники / независимость не подтверждена», с пояснением.

## Проверки

Быстрые тесты запускаются без скачивания модели:

```powershell
python -m unittest discover -s tests -v
```

Они проверяют разбор RSS/Atom, фильтрацию и нормализацию материалов, дедупликацию, окно дат, логику группировки на контролируемых сходствах и обязательные редакторские отметки. Тест группировки подменяет модель контролируемыми векторами: стандартный набор не скачивает и не загружает её веса. В `tests/model_integration.py` отдельно лежит необязательная проверка настоящей мультиязычной модели. Чтобы запустить её, установите зависимости из `requirements.txt`, задайте `RUN_MODEL_INTEGRATION=1` и выполните в PowerShell `python -m unittest discover -s tests -p "model_integration.py" -v`. Первый запуск может скачать веса модели. Интеграционная проверка не утверждает, что модель безошибочно различает события: каждый объединённый пункт нужно проверить редактору.

## MAX

Для публикации создайте бота MAX, добавьте его администратором в нужный канал с правом публикации и задайте переменные окружения:

```powershell
$env:MAX_BOT_TOKEN = "..."
$env:MAX_CHANNEL_ID = "..."
```

Сначала используйте `python -m app publish ID --dry-run`. Реальная отправка производится только после статуса `approved`. Повторная отправка опубликованного черновика блокируется. Токен не записывается в конфигурацию или журнал.

Для автоматической публикации по расписанию доступна команда `python -m app publish-scheduled`. Она рассматривает только явно выбранную часть сегодняшней партии со статусом `approved` и сохранёнными отметками редакторской проверки. Общая функция `publish` повторно проверяет выбор и дневной лимит и применяется также к ручной команде `python -m app publish ID`: за один московский календарный день разрешён только один основной пост независимо от способа запуска. Перед отправкой SQLite атомарно резервирует слот; активная или неопределённая попытка блокирует второй основной пост за этот день до разрешения результата через `publish-resolve`. Исправления, созданные командой `correct`, дневной слот не занимают. Если часть не выбрана или не хватает отметок, плановая команда ничего не отправляет и записывает причину.

### Партии сводок и выбор дневной части

Все части, созданные одним запуском `draft`/`run`, входят в одну партию с общим ID и нумерацией. При первом запуске новая схема также связывает старые черновики, если их `part_ids` сохранены в журнале. До публикации редактор явно выбирает ровно одну часть. Планировщик публикует только выбранную и одобренную часть партии за текущую дату; если выбор не сделан или эта часть не одобрена к 14:00, публикация пропускается без автоматического выбора другой части. Ручная команда `publish ID` также требует выбора части. Исправления этим правилом не ограничены.

Workflow:

```powershell
python -m app review batches
python -m app review batch-show BATCH_ID
python -m app review select-part BATCH_ID DRAFT_ID
python -m app review close-part BATCH_ID DRAFT_ID --reason "Не вошло в дневной пост"
# или вместо закрытия:
python -m app review defer-part BATCH_ID DRAFT_ID --until 2026-10-19 --note "Нужно дополнительное подтверждение"
```

Выбор другой части снимает выбор с прежней; решение сохраняется в журнале. Выбранную часть нельзя закрыть или отложить, пока редактор не выберет другую. Закрытые и отложенные черновики остаются в истории со статусом `rejected`, а причина и решение хранятся отдельно в партии. Для каждого утверждения команда `batch-show` показывает исходное время публикации материала и предел актуальности в 96 часов. Перенос разрешён только на дату, начало которой попадает в этот срок. Когда дата переноса наступила, материал может попасть в новую партию, только если он ещё не старше 96 часов; просроченные материалы фильтруются. Их исходные даты сохраняются в доказательствах и показываются редактору.

### ReliefWeb API для OCHA

ReliefWeb предоставляет публичный read-only API, однако с 1 ноября 2025 года запросы требуют предварительно одобренного `appname`. Получите appname у ReliefWeb, задайте его в окружении как `RELIEFWEB_APPNAME`, затем явно включите `unocha_ukraine` в `sources.yaml`. До этого источник выключен. Запрос ограничен материалами с `source.shortname=OCHA` и кодом страны `UKR`; он получает заголовок, дату, ссылку и метаданные, не полный текст отчёта. В ответах могут быть материалы партнёров, поэтому права на исходный документ нужно учитывать отдельно. Не копируйте полный текст, карты или изображения. [Документация API и условия использования](https://apidoc.reliefweb.int/).

## Журнал и данные

SQLite база создаётся в `data/app.sqlite3`. Она содержит исходные материалы, нормализованные записи, неизменяемые версии материалов, черновики и события журнала. Повторное получение той же канонической ссылки от того же источника обновляет исходный кэш и время последней проверки, а не добавляет строку в `raw_items`. При изменении заголовка, описания или даты создаётся версия с номером, временем обнаружения и перечнем изменённых полей; прежние версии сохраняются. Черновик связывает утверждение с конкретной версией, а его текст, дата и ссылка остаются снимком этой версии. Если новая версия относится к утверждению в pending- или approved-черновике, приложение создаёт предупреждение; approved-черновик возвращается на редакторскую проверку. Опубликованные черновики не меняются. Команда `python -m app logs` показывает последние события. Ручная коррекция публикуемого текста фиксируется отдельным событием.

Нормализованные материалы уникальны в пределах источника по паре «источник + каноническая ссылка», а не глобально по URL. Поэтому одна и та же страница, пришедшая из разных источников, сохраняется как отдельное утверждение и отдельное основание в черновике. Она помечается как повторная ссылка и не может быть принята редактором за независимое подтверждение в проверке группы. Повтор по текстовому отпечатку также ищется только внутри того же источника. При обновлении старой базы таблица `items` перестраивается с сохранением ID и ссылок черновиков.

## Расписание

На Windows установите расписание из активированного окружения приложения:

```powershell
python -m app schedule install
python -m app schedule status
```

Приложение зарегистрирует две ежедневные задачи для текущего пользователя Windows:

1. В 12:00 по местному времени — сбор материалов и создание черновика со статусом `pending`; приложение пытается уведомить редактора, что черновик готов. Если материалов нет, оно тоже записывает и сообщает причину.
2. До 13:45 редактор проверяет даты событий, источники и группировки и одобряет черновик.
3. В 14:00 — `publish-scheduled`. Публикуется только явно выбранная и одобренная часть партии. Если редактор не выбрал часть или не успел её одобрить, пост пропускается без автоматического выбора альтернативы; причина записывается в журнал и приложение пытается показать уведомление Windows. Windows может скрыть уведомление настройками фокусировки или уведомлений; результат попытки тоже записывается.

Задачи выполняются только пока текущий пользователь вошёл в Windows. Установщик проверяет идентификатор часового пояса Windows (`Russian Standard Time`, отображаемый как «(UTC+03:00) Москва, Санкт-Петербург»), а не только текущее UTC-смещение. Поэтому другая зона, совпадающая с Москвой летом, не пройдёт проверку, если её зимнее смещение отличается. Команда `schedule status` показывает обнаруженный идентификатор. Задачи используют Python, из которого запущена команда `schedule install`; поэтому выполните её из `.venv`. Переменные `MAX_BOT_TOKEN` и `MAX_CHANNEL_ID` должны быть доступны этому пользователю Windows, а при включённом OCHA API — также `RELIEFWEB_APPNAME`. Переменные, заданные только через `$env:` в открытом PowerShell, не гарантируют доступность после входа в Windows. Токен не записывается в параметры задач.

Проверить расписание и следующий запуск: `python -m app schedule status`. Удалить зарегистрированные приложением задачи: `python -m app schedule remove`. Чтобы проверить, что именно будет опубликовано, используйте `python -m app publish-scheduled --dry-run`. При пропуске публикации подробная причина доступна в `python -m app logs`. Повторный запуск после успешной публикации не создаст второй основной пост за день.

## Ограничения первой версии

- Получает RSS и настроенный ReliefWeb API; произвольные сайты не сканирует.
- AP, Reuters, BBC, ISW, Bellingcat и прочие источники без подтверждённого разрешённого канала требуют ручного добавления редактором.
- Фильтрует по дате публикации, а не по дате самого события. Автоматически дата события не устанавливается; редактор должен проверить её и указать явно для более раннего события.
- Источники с `enabled: false` пропускаются.
- Используйте короткие пересказы и ссылки, а не копии статей и медиаматериалов.
- Не вносите в пост точные координаты, текущие перемещения, позиции и иные оперативные подробности.
